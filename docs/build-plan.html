01Scope & principles

The system is not an Excel analyser. It is an R20 importer, a permanent membership database, a zone/district classification engine, a historical analytics engine, a membership-movement tracker, an executive dashboard, an R20 export system, and a reporting platform — built in that order.

Design principles carried through every phase

  • Employee Number is the identity key. Names change spelling, order, and titles; the employee number is the only reliable link between one month's R20 and the next.
  • Snapshots are immutable. July is never replaced by August. Each approved monthly R20 becomes a permanent membership_snapshot; history is the product.
  • Nothing enters the permanent tables unreviewed. Every upload lands in a staging table, is validated, and is explicitly approved by a Data Officer before it becomes history.
  • Describe movement, don't assume cause. The system says "added to R20" / "no longer in R20", not "joined" / "left", until an executive records a verified reason.
  • Regional vs zone movement are different events. A member who moves from Kumasi Zone to Adansi Zone is retained regionally but a transfer-out for Kumasi and a transfer-in for Adansi. This distinction is built into the analytics model, not bolted on.
  • Access is server-enforced. A Zone Executive cannot see another zone's members by editing a URL. Row-level security and server-side authorization checks, not just hidden menu items.
MVP boundary Version 1 delivers: secure login, the 18-zone + district + alias master data, R20 upload → validate → stage → approve → snapshot, two-period comparison (net change, growth %, retained / added / missing), zone & district analysis, zone ranking, the regional dashboard, per-zone Excel exports, and the R20 archive. PDF reports, multi-month charts, member profiles, movement-reason tracking, and PWA install are Version 2.

Quirks the importer must absorb (all seen in the real files)

  • "X" vs "X Municipal Assembly": the Regional file uses long forms (Kumasi Metropolitan Assembly, Bekwai Municipal Assembly) where zone sheets use short ones. The alias list covers every case seen.
  • Recurring misspellings: Kwabere East Municipal Assembly (extra "e") sits alongside Kwabre East... in both the Regional file and a zone workbook's own DISTRICT column. Ejura-Sekyedumase (Regional) vs Ejura-Sekyeredumase (sheet). Both aliased.
  • Header-only / near-empty district sheets: e.g. Juaben Municipal (1 member). Valid; count what is there.
  • Ghost rows: earlier file versions had sheets reporting 100+ rows with only the header populated. Count non-empty rows, not the row range.
  • Blank rows and a trailing 6th column in some sheets: drop empty rows, ignore empty trailing columns. Also ignore unused Sheet2 / Sheet3 and any sheet without the five R20 headers.
  • Dirty sheet names: trailing non-breaking space, leading space, and the typo KWABRE EAST MUNNICIPAL. Normalisation folds these.
  • Name spacing and missing titles: double spaces, a leading space, some names with no Mr./Mrs./Miss. Collapse spaces; keep the raw value for audit.
  • Employee number as a number: one zone-workbook row held 1530485 as a numeric cell, not text. Coerce to text on read; preserve leading zeros.

05Data model

Tables from the blueprint, grouped by role. Full column lists live in the migration files; this is the shape.

Master / reference

  • regions — one row: Ashanti.
  • zones — the 18, seeded. region_id, zone_code, is_active.
  • districts — 44, seeded from the map above. zone_id, district_code, is_active.
  • district_aliases — district_id, alias, normalized_alias (unique). Seeded from every DISTRICT string seen; grows as unmapped names are resolved.
  • roles — Super Admin, Regional Admin, Regional Executive, Regional Data Officer, Zone Executive, District Executive, Viewer.
  • users — role_id, optional zone_id / district_id scope, is_active.

Ingestion

  • reporting_periods — month + year, label, is_locked. One approved Regional R20 per period.
  • r20_uploads — file_hash (duplicate-upload guard), status (Uploaded → Validating → Needs Review → Validated → Approved → Imported → Locked), row counts, processing_notes.
  • r20_staging_rows — every raw row + normalised values + validation_status + mapped_district_id / mapped_zone_id. The quarantine buffer.

History (never overwritten)

  • members — one row per employee_no (unique index), with current_* pointers and first_seen_period / last_seen_period.
  • membership_snapshots — one row per member per period: exactly where they appeared that month, including raw_district and resolved district_id / zone_id. This table is the analytical dataset.
  • membership_movement_reasons — optional verified reason per member per period (Version 2).
  • audit_logs — every upload, approval, mapping change, export, user change, unlock.
Analytics are derived, not stored Net change, growth %, retention, rankings, and transfer in/out are computed from membership_snapshots on demand (with caching), so a corrected mapping or a late reason update flows through without a migration.

depends on: Phase 0

PHASE 2

R20 importer

Done

A reliable, forgiving Excel processing engine: the heart of the system.

  1. Upload — store original to the private bucket under {year}/{month}/, SHA-256 file_hash, warn on exact re-upload, create the reporting_period and r20_uploads row.
  2. Workbook reader (lib/r20/parser.ts, ported from analyzer/) — header detection, skips Sheet2/3 and non-R20 sheets, drops blank rows, ignores trailing empty columns, handles ghost-row sheets and numeric employee-number cells.
  3. Normalisation + validation — employee number to text, name spacing, region check; flags missing / duplicate employee numbers.
  4. District mapping (lib/r20/mapping.ts) — alias engine resolves every DISTRICT string to a district and its zone; unresolved go to a queue.
  5. Staging — every row written to r20_staging_rows with its resolved district/zone; counts rolled up to r20_uploads. Tested: real July R20 stages 6,653 rows, 0 unmapped.
  6. Validation dashboard (§53) — source rows, valid members, blank rows ignored, duplicates, missing numbers, unmapped districts, status.
  7. Unmapped-district resolver — pick a district once; it is saved as an alias and the upload's rows re-resolve immediately.
  8. Zone & district classification panel — the moment an R20 is uploaded it shows member counts sorted into all 18 zones, expandable to districts.

Upload a Regional R20 → accurate validation report + live zone/district breakdown; resolve mappings interactively. Live.

depends on: Phase 1

PHASE 3

Approve & snapshot

Done

Turn an approved upload into permanent history.

  1. Approve & import — one transactional Postgres function (import_upload, migration 0005): upserts members by employee number, keeps the first occurrence of any duplicate, writes one immutable membership_snapshot per member, sets first/last_seen_period.
  2. Rows still unmapped or missing an employee number are excluded, with the count shown before you confirm.
  3. Upload → imported; audited.
  4. Period locking (set_period_lock) — Admin only, audited.
  5. Refinement: last-seen tracking assumes forward imports; will compare by year/month when out-of-order months are loaded.

January R20 imported: 6,932 members + snapshots, 1 row excluded. Live.

08Risks & how the plan handles them

  • Mapping drift. District names on the payroll change over time. Mitigation: aliases are data, resolved once by an admin, audited, never in code.
  • A member counted as lost when they only transferred zones. Mitigation: internal-movement logic is a Phase 4 acceptance criterion with its own tests (blueprint §76 test cases).
  • Bad upload corrupting history. Mitigation: staging table + explicit approval + period locking; snapshots are append-only.
  • Large file timeouts. Mitigation: importer runs as a background function from Phase 2, not retrofitted.
  • Wrong conclusions from a data-quality problem. Mitigation: the validation dashboard separates "blank rows ignored, duplicates" from real membership movement; data-quality score in Phase 8.
  • Zone workbooks contradict the Regional file. Mitigation: the Regional R20 is the single membership source; workbooks feed structure only. Settled — see §3.
  • Thin change signal. July→August moved only +13 net with 4 internal movers, so the transfer logic is under-exercised by real data. Mitigation: the §76 synthetic test cases cover zone/district moves explicitly.
